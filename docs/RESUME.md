# 新規チャットからの再開手順

## 固定プロンプト

```text
@GitHub https://github.com/dharmainsight/structural-visualization- の開発を再開してください。mainと未マージのPRを確認し、最新のdocs/RESUME.mdおよびdocs/PLAN.mdに従って作業を継続してください。
```

## 目的と前提

GitHub を開発状態の正本とする。過去チャット、記憶、会話の要約は再開の前提としない。新規チャットの入力とリポジトリにある資料だけで作業を開始する。原典由来の主張を追加する際はユーザーが提示した該当箇所を実際に確認する。保存済みの要約だけをもって原文を再確認したとは言わない。

このファイルは開発の再開手順を定義する。現在の段階・完了条件・未確認事項・次の入力の正本は PLAN.md。正式見出しと章節構造の正本は TOC.md。スキル本体は structural-visualization/SKILL.md。開発用の手順を実行時スキルに混入させない。

## 1. 最新状態の取得

1. GitHubでリポジトリ dharmainsight/structural-visualization- の default branch、最新コミット、開いているPR（特に開発進捗に関係するPR）を取得する。
2. main の docs/RESUME.md と docs/PLAN.md と docs/TOC.md を確認する。未マージの開発PRがあり、進捗の更新が含まれる場合は、PRのhead SHAを取得して同じファイルを読む。mainに本ファイルがまだない場合も、関連PRのheadで探す。
3. PRがマージ済みならmainの実際のファイルを読み直す。未マージならそのPRの進捗をレビュー中の作業状態として扱い、承認済みと混同しない。単なる更新日時ではなく、mainとの差分・コミットの継承・目的の整合を照合する。
4. 最新の一貫した作業基点を選ぶ。競合する複数の開発PRや閉じられた未マージPRがある場合、差分を確認し、採用されていない内容を黙って復活させない。閉じられたPRにしか再開情報がない場合は、その情報を参考にmainとの差分と選択肢を報告する。重要な矛盾が解消できなければ確認を求める。
5. 選んだ同一refから PLAN.md、TOC.md、必要な節の references/sources.md、structures.md、個別構造の参照ファイル、SKILL.md、evals/CASES.mdを読む。取込作業なら docs/KNOWLEDGE-TRANSFER.md を読む。必要な範囲だけ取得し、過去のチャットや書籍全文を要求しない。

GitHubにアクセスできない場合は最新状態を確認できないと明記し、推測でコミットや進捗を再構成しない。

## 2. 次の作業の決定

PLAN.mdのチェックポイントと完了条件を確認し、進行中の最小の作業単位を特定する。

- 原典が必要で未提示：PLAN.mdの資料要求キューからNEXT行を取得し、同じrefのTOC.mdで全IDの正式見出しと親IDを照合する。章・上位節の正式見出しと小見出しを台帳からそのまま案内する。取得目的・推論・図の要求は見出しと別に記述する。付属図は該当箇所にある場合のみ共有を依頼する。既に確認済みの資料は通常、再提出不要。
- **見出し照合が成立しなければ資料要求を停止する。** TOC.mdがない、IDがない、見出しが一致しない、親子関係が不明、版差がある場合は、正確な見出しを確認できない理由を説明し、必要な目次箇所だけを確認する。本文の内容予想や汎用的な項目名を正式見出しとして作らない。TOC掲載のみを本文確認済みと扱わない。
- 新しい原典が提示済み：提示された範囲を確認し、出典台帳と独自の操作規則を更新する。原典の説明、独自の設計、未確認事項を区別する。
- 原典確認以外の作業：現行の成果物を読み、PLAN.mdの完了条件に沿って実装・評価を進める。必要であれば優先度や作業範囲の調整を記録する。

著作物の本文・図版・スクリーンショットは公開リポジトリへ保存しない。原典の代替にならない独自の操作知識、短い要点、書誌・参照情報のみを記録する。

## 3. 更新と検証

- 関連する未マージPRが継続中であり、同じ作業範囲ならそのheadから追加コミットする。マージ済みなら最新mainから新しいブランチとPRを作る。既存変更を上書き・強制更新しない。
- 変更対象に応じて SKILL.md、参照ファイル、出典台帳、評価ケース、PLAN.md を同じ作業単位で更新する。既存の原典要約・評価IDを保持する。
- 参照先の存在、変更差分、ファイル内容、評価ケースの件数、実際に行った検証の結果を確認する。資料要求キューのID・正式見出し・親子関係を照合する。実行環境があればリポジトリルートで node scripts/check-source-requests.mjs を実行する。実行環境がなければ同じ検査を読み取ったファイルに対して実施し、実行していない自動試験を合格としない。仕様の追加を試験合格と混同しない。
- ユーザーの明示的な指示なしにPRをマージしない。書籍の再提示が必要な場合は理由と対象を限定する。

## 4. セッション終了チェック

各チャットの作業終了前に PLAN.md の再開チェックポイントを更新する。次回のチャットに次の内容が伝わるようにする。

| 項目 | 記録内容 |
|---|---|
| 更新日 | 実際の更新日 |
| 現在地 | 開発段階と完了条件 |
| 確認済みの原典 | 出典ID、章・節、確認範囲 |
| 実装済み | 変更内容とファイル |
| 検証済み | 実施した検証と結果 |
| 未確認・課題 | 原典・実装・評価を区別 |
| 次の作業 | 次の具体的な作業と必要な入力。資料要求キューの目次ID・正式見出しを同一refのTOCと照合 |
| GitHub状態 | 関連PRの番号・ブランチ。マージ状態は再開時に再取得 |

PRへの反映と実際のheadを確認し、ユーザーには変更点・PRリンク・残る課題・次に必要な入力を簡潔に伝える。固定プロンプトは段階が変わっても更新不要。

## 5. 再開時の応答

最初の応答は、確認したPR状態、現在の段階、次の作業、必要な入力（ある場合）を最小限に示す。資料を要求する場合は照合済みの正式見出しを使用し、取得目的と区別する。必要資料が揃っていればそのまま作業する。目的や方針を毎回説明し直さない。

# 新規チャットからの再開手順

## 固定プロンプト

```text
@GitHub https://github.com/dharmainsight/structural-visualization- の開発を再開してください。mainと未マージのPRを確認し、最新のdocs/RESUME.mdおよびdocs/PLAN.mdに従って作業を継続してください。
```

## 正本と取得順

GitHubを開発状態の正本とする。過去チャットや記憶を前提にせず、次を確認する。

1. default branch、最新コミット、開いているPRとhead SHAを取得する。
2. mainの本ファイルと `docs/PLAN.md` を読み、関連する未マージPRの同一ファイルと差分を照合する。
3. コミットの継承と作業目的を確かめ、一貫した基点を選ぶ。PRの更新日時だけで決めない。閉じられた未採用案を黙って復活させない。
4. 同じrefの `structural-visualization/SKILL.md`、必要な参照、`evals/CASES.md`、`evals/RESULTS.md` を読む。

現在の主対象は、特定資料に依存しない一般化された構造化スキル。実行時ディレクトリに書名・著者名・章番号・出典台帳・開発履歴を戻さない。事実や数値の根拠、不確実性、仮説の区別は維持する。

## 作業の決定

- PLANの次の作業と最新のユーザー指示に従う。完成済みの基本取込を繰り返さない。
- 不具合があれば、再現入力、期待する関係、実際に失われた情報を特定してから修正する。
- 未マージPRに同じ作業があればそのheadから継続する。マージ済みなら最新mainから新規ブランチとPRを作る。
- 新たな資料は、具体的な未解決事項に必要な場合だけ求める。既存の目次を使った要求が必要なら `docs/TOC.md` のID・正式見出し・親子関係を照合し、存在を確認できない見出しを作らない。
- 開発上の過去記録は `docs/archive/` にある。実行時スキルの内容や現在の未完了事項と混同しない。

## 変更と検証

1. 判断規則、必要な例、評価ケース、計画を同じ作業単位で更新する。既存評価IDは再利用せず、新規IDを末尾へ追加する。
2. `node scripts/check-skill.mjs --self-test`、`node scripts/check-skill.mjs`、`node scripts/check-source-requests.mjs` を実行する。
3. 内容を変更した場合、該当する既存ケースと新規入力を適用し、入力・出力・実施条件・判定を記録する。期待回答を実行担当に渡さない。
4. 形式検査、モデル適用、人間の理解度比較、描画の実見は別の検証として記録する。未実施のものを合格にしない。
5. インストールする場合は、その環境の個人スキルの保存手順で同じ内容を検証・保存し、実際の保存先を確認する。リポジトリへの反映とインストールを混同しない。
6. ユーザーの明示的な指示なしにPRをマージしない。既存変更の上書き・強制更新をしない。

## 終了時

PLANの現在地、変更内容、実施済み検証、未確認事項、次の作業、ブランチ・PRを更新する。PRの実際のheadと状態を再取得する。ユーザーには完成した内容、検証範囲、PR、必要な次の操作だけを簡潔に伝える。固定プロンプトは変更しない。
